# 운영 이미지 전환과 복구 준비

관련 이슈: #282, #285, #288

이 문서는 실행 승인이 아니라 **배포 전 확인 조건**이다. 현재 CD를 그대로 실행해도 무중단으로
전환된다는 뜻이 아니다. 운영 업로드 설정을 끄거나 클라이언트를 변경하지 않는다.
실제 계정, 접속 정보, 토큰, DB 행, presigned URL은 이 문서나 PR에 넣지 않는다.

## 1. 현재 구조와 확인된 위험

- `docker/docker-compose.prod.yml`은 앱 하나를 호스트 8080에 연결하고 가변 `prod` 태그를 쓴다.
- 기존 `.github/workflows/cd-prod.yml`은 main push/수동 실행 시 바로 앱을 교체했다.
  `up -d --remove-orphans`는 별도 슬롯 구성 없이 실행하면 기존 컨테이너를 없앨 수 있다.
  health 성공만 검사하고 이전 이미지로의 자동 복구는 구현하지 않았다.
- 앱 시작 때 Flyway migration 후 Hibernate validate를 한다. 새 앱을 같은 DB에 시험 실행하는
  것만으로 DB가 변경될 수 있다. 단순 health 시험으로 취급하지 않는다.
- V26 이후 `place_type` 없는 옛 식당 INSERT는 실패한다. V27은 적용 당시 매거진만 집계행을
  만들므로, 적용 후 옛 방식으로 생성한 매거진은 집계행이 없다.
- 새 이미지 연결은 기존 파일키를 NULL로 둘 수 있다. 새 앱이 이런 데이터를 쓴 뒤에는
  옛 앱으로 트래픽만 돌려도 사진이 보존된다고 가정할 수 없다.

**업로드 flag 유지와 요청 무중단은 별개다.** DB DDL의 잠금, 단일 앱 교체, 프록시 전환도
요청에 영향을 준다. 기존 업로드 API 발급뿐 아니라 사진 연결 완료까지 확인해야 한다.

## 2. 권장 전환안과 아직 필요한 검증

### 배포 실행 제한

이 변경은 운영 CD의 push 트리거를 제거한다. main에서 수동 실행하고, 검증한 전체 커밋 SHA가
실행 SHA와 일치하며 `transition_verified`를 명시적으로 확인해야 빌드/인증 단계로 진행한다.
기본 확인값은 false다. develop 대상 PR 병합 자체는 운영 CD를 실행하지 않는다.
이 변경이 main에 반영되기 전에는 main의 기존 자동 배포가 그대로 남아 있다.

확인 입력은 실수 방지 장치이지 독립 승인이나 시험 결과의 자동 검증이 아니다. GitHub prod
environment 승인 정책은 별도이며, 운영자는 아래 증거가 없으면 확인값을 켜지 않는다.
배포 스크립트의 실제 교체 동작은 아직 단일 슬롯이다. 이 제한을 통과했다고 무중단 전환이나
DB 호환성이 해결되는 것은 아니며, 전환 장치 시험이 끝나기 전에는 수동 실행도 하지 않는다.

권장 후보는 **기존 앱 유지 → 호환성 확보 → 별도 새 앱 검증 → 프록시 전환 → 기존 앱 정리**다.
구 앱과 새 DB의 호환성이 확인되기 전에는 이 순서를 실행하지 않는다.

```text
현재 앱 + 기존 업로드 (계속 서비스)
             │
             ├─ 배포 이미지/설정 고정, 복구 자료와 백업 복원 시험
             ├─ 구 앱 쓰기와 신규 스키마 호환성 검증
             └─ 신규 이미지 인프라 준비와 검증
                          │ 모든 조건 충족
                          ▼
DB 변경 1회 실행 → 별도 포트의 새 앱 검증 → 프록시 전환
                          │
                          └─ 새 DB/이미지 형식 호환 복구 앱 준비
```

다음 중 실제로 검증한 호환 방안이 있어야 한다.

1. 구 앱을 신구 스키마와 호환되게 만드는 별도 변경. 적용 전후와 중간 스키마에서 실제 옛 앱
   기동/쓰기/읽기를 검증한다. 이미 병합한 V26/V27은 수정하지 않는다. V46 같은 마지막
   보완만으로 V26~V45 실행 중 생기는 위험까지 해결했다고 판단하지 않는다.
2. 호환되지 않는 **관리자 식당·매거진 쓰기만** 잠시 제한하는 방안. 적용할 정확한 요청과
   내부 작업을 파악하고 담당자 승인을 받아야 한다. 기존 업로드/완료 요청을 함께 막지 않는다.
   이미 처리 중인 요청을 drain하고, 우회 경로와 백그라운드 쓰기가 없음을 확인한다.
   제한 중 사용자의 업로드 흐름이 보존되는지 시험하지 않았다면 이 방안도 실행하지 않는다.

아직 어느 방안도 실제 운영 앱과 프록시에서 검증 완료한 상태가 아니다. 이 문서는
관리자 쓰기 제한, DB trigger 추가, 운영 설정 변경을 수행하지 않는다.

## 3. 적용 전 체크리스트

### 배포 대상과 복구 자료

- [ ] 릴리스 SHA, 앱 이미지 digest, worker ZIP SHA-256, 규격 버전/digest를 고정한다.
      RN 인증을 이번 이미지 릴리스에 포함할지 별도로 결정한다.
- [ ] 현재 앱 이미지 digest와 설정을 비공개 저장소에 보존한다. `prod` 태그만 기록하지 않는다.
- [ ] DB 변경 후에도 동작하는 복구용 앱 digest를 확보한다. 현재 옛 앱이 그 역할을 할 수
      있다고 가정하지 않는다. 새 이미지 데이터 읽기/쓰기를 포함해 시험한다.
- [ ] DB 백업의 완료 상태, 보존 기간, 복원 위치, 복원 시험 결과를 확인한다.
      백업 이후 계속 들어온 예약/리뷰/사진 연결을 어떻게 보존할지 정한다.
      오래된 백업으로 원래 DB를 덮어쓰는 절차는 사용하지 않는다.

### DB와 앱

- [ ] 실제 Flyway 현재 버전/checksum/실패 이력과 릴리스 migration 목록을 대조한다.
      이 문서의 V14→V45는 고정 회귀 시나리오이며 운영 현재값을 대신하지 않는다.
- [ ] NULL/길이/중복 등 migration guard와 기존 enum 데이터의 새 코드 호환성을 확인한다.
      운영 원본 데이터는 로컬로 내보내지 않는다.
- [ ] 예상 데이터 규모에서 DDL 잠금과 실행 시간을 시험한다. 장기 트랜잭션이 있으면 시작하지 않는다.
- [ ] 다른 배포/수동 migration과 중복 실행되지 않게 작업 소유자를 하나로 정한다.
- [ ] 구 앱의 쓰기 겹침 대책을 시험한다. 식당/매거진 반례만으로 전체 경로를 검증했다고 보지 않는다.
- [ ] 새 앱이 schema validate, 실제 읽기/쓰기, 인증, 기존 사진 조회를 통과한다.

### 업로드와 전환 장치

- [ ] 기존 업로드 origin/키/버킷/권한은 유지한다. 자동 삭제와 기존 사진 일괄 전환은 별도다.
- [ ] 신규 S3/SQS/worker/결과 consumer와 규격이 일치하고 발급→PUT→READY→조회가 성공한다.
      V15의 새 제어행은 초기 v1/OFF다. 기존 업로드를 끈 것이 아니며,
      검증된 새 경로를 준비하기 전에 새 앱으로 트래픽을 보내지 않는다.
- [ ] 새 앱은 별도 loopback 포트/고유 컨테이너 이름으로 띄울 수 있도록 준비한다.
      기존 compose/CD를 그대로 병렬 실행하지 않는다. 프록시 구성은 비밀을 제외하고 따로 검토한다.
- [ ] 두 앱과 모니터링의 최대 메모리/CPU/DB 연결 합계를 확인한다. 현재 순간 여유만으로
      동시 기동 가능하다고 판단하지 않는다. 용량이 부족하면 별도 호스트 등 대안을 먼저 준비한다.
- [ ] 새 슬롯의 자동 migration/정리/중복 작업 실행 여부를 명시한다. schema 변경은 단일
      실행 주체가 담당한다. 검증 슬롯이 운영 DB를 임의 변경하지 않도록 한다.
- [ ] 프록시 설정 검사, 기존 연결 drain, 전환/되돌리기를 로컬 또는 개발에서 시험한다.
      외부 health뿐 아니라 업로드 발급·연결 완료 요청의 성공 여부를 연속 관찰한다.
- [ ] 단계별 시간 제한과 중단 조건을 실제 시험 결과로 정한다. 실패 시 자동 재시작/재배포를
      반복하지 않는다. 단계 완료 근거가 없으면 다음 단계로 가지 않는다.

## 4. 단계별 실패 대응

| 실패 시점 | 대응 | 하면 안 되는 일 |
| --- | --- | --- |
| DB 변경 전 | 새 슬롯/배포 시도를 멈추고 현재 앱 유지. 원인 수정 후 재검증 | 현재 업로드 OFF, 기존 앱 제거 |
| migration 일부 적용 후 | 실패 SQL과 실제 스키마/이력을 대조. 호환 확인된 경로만 유지하고 영향 요청을 별도 판단. 검토된 보완으로 앞으로 복구 | 무조건 재실행, `clean`, 이미 적용된 SQL 수정, 이력만 `repair` |
| DB 변경 완료, 전환 전 | 새 앱 검증 실패 원인 수정. 옛 앱 유지 여부는 새 스키마 호환 시험 결과로 판단 | 옛 앱이면 안전하다고 가정 |
| 전환 후, 새 형식 쓰기 전 | 구/신 스키마 호환이 확인되고 새 데이터가 없다는 근거가 있을 때만 이전 슬롯 복귀 검토 | health만 보고 이전 슬롯 복귀 |
| 새 이미지/새 형식 쓰기 후 | 새 형식을 이해하는 검증된 복구 앱으로 전환하거나 수정 버전 배포. DB/S3/queue 상태 보존 | V14 앱으로 무조건 복귀, S3 파일 삭제, 과거 DB 덮어쓰기 |

MySQL의 DDL은 암묵적 commit을 일으킨다. 뒤 SQL이 실패하거나 JDBC rollback을 호출해도
앞서 성공한 DDL이 자동 취소되지 않는다. Flyway `repair`는 이력을 다루며 이미 바뀐 테이블을
원상복구해 주지 않는다. 먼저 실제 DB 상태를 확인하고 복구 SQL 및 재실행 범위를 따로 검토한다.

DB 복원이 불가피하면 별도 DB에 복원하고 복원 시점 이후 쓰기와 S3/queue 차이를 확인한다.
데이터 손실 범위 및 요청 제한이 필요하다면 별도 승인을 받는다. 이 문서는 그런 상황에서도
업로드가 절대 중단되지 않는다고 보장하지 않는다.

## 5. 이번 회귀 시험의 범위

`ProductionTransitionMigrationTest`는 외부 환경변수 DB가 아니라 새 Testcontainers MySQL을 쓴다.
고정 V14→V45의 합성 데이터 보존, 옛 쓰기 방식 반례, 신규 제어행 초기값,
DDL 부분 적용과 rollback 한계를 검사한다. 기대한 반례를 재현한 테스트도 PASS에 포함된다.

이 시험은 운영 데이터 전체/JPA/실제 프록시 전환/백업 복원/운영 업로드 연속성을 증명하지 않는다.
DDL probe는 독립된 시험 테이블에서 JDBC로 실행한다. 실제 Flyway 실패 이력의 복구나
`repair` 실행을 시험한 것이 아니다.
절차와 테스트가 병합돼도 위 체크리스트가 미완료라면 운영 배포 판단은 NO-GO다.
