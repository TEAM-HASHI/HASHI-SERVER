# 식당 사진 탭 연동

기준: `HASHI-PLAN`의 `RESTAURANT_PHOTO.md` (`a2990f8`). 동영상과 내부·외부·음식 분류는 이번 API에 포함하지 않는다.

## 조회

`GET /api/v1/restaurants/{restaurantId}/photos?filter=ALL`

로그인 없이 호출할 수 있다. 한 번에 최대 20장을 반환하며 `size`는 받지 않는다.

| 필드 | 사용 방법 |
|---|---|
| `filter` | `ALL`, `REPRESENTATIVE`, `MENU`, `REVIEW`. 기본값 `ALL` |
| `counts` | 전체·대표·메뉴·리뷰 필터 칩의 개수 |
| `totalCount` | 선택한 필터의 전체 개수 |
| `photos` | 현재 페이지. `photoId`로 항목을 구분하고 `imageUrl`로 표시 |
| `photos[].image` | asset 이미지의 상태·반응형 이미지 후보. legacy 사진은 `null` |
| `nextCursor` | 추가 조회의 `cursor` 값. 마지막이면 `null` |
| `hasNext` | `false`면 추가 조회 중단 |

필터를 바꾸거나 리뷰 작성 후 돌아오면 `cursor`를 생략하고 처음부터 다시 조회한다. 이 API는 페이지 간 스냅샷을 보관하지 않는다. 사진 추가·삭제 중에는 앞 페이지와 순서가 달라질 수 있으므로 화면을 갱신할 때 기존 목록을 교체한다. 같은 데이터의 연속 조회에는 중복·누락이 없다. 커서는 대표 표시순서·ID, 리뷰 생성시각·리뷰 ID·사진 표시순서·ID, 메뉴 ID와 혼합 진행 위치를 담는다. 앞 페이지 항목이 삭제되어도 offset이 밀려 사진을 건너뛰지 않는다. 대표사진 재정렬이나 동일 원본의 출처 변경은 스냅샷으로 고정하지 않으므로 새로 조회한다.

다음 요청은 `?filter=ALL&cursor={nextCursor}`로 보낸다. 커서는 기존 일반 피드와 같은 Base64url 구조 검증 방식이며 서명된 권한 토큰이 아니다. 식당·필터 불일치와 잘못된 값은 거절한다. 클라이언트는 해석·수정하지 않고 그대로 재전송한다.

빈 결과는 `200`, `photos=[]`, `hasNext=false`다. 없는 식당과 삭제된 식당은 `404 / RESTAURANT-004`, 잘못된 필터·커서 또는 다른 식당/필터의 커서는 `400 / COMMON-400`이다.

## 순서와 같은 원본 판별

- 대표사진: 관리자가 정한 표시 순서, 동률이면 ID 순.
- 메뉴사진: 메뉴 등록 ID 순. 사진 없는 메뉴는 제외.
- 리뷰사진: 리뷰 생성 시각 내림차순, 동률이면 리뷰 ID 내림차순, 리뷰 안에서는 사진 표시 순서·사진 ID 순.
- 전체: 동일 원본 참조를 제거한 뒤 대표 1장·리뷰 3장을 반복하고, 한 출처가 끝나면 남은 출처를 이어서 표시한다. 메뉴는 마지막이다.

동일 원본은 asset ID 또는 같은 원본 파일 키로 판단한다. 파일 키는 대소문자를 구분하며 API 응답에는 노출하지 않는다. 같은 사진을 서로 다른 파일로 다시 올린 경우까지 이미지 내용을 비교하지는 않는다. 전체에서 중복을 제거하므로 `counts.all`은 나머지 세 개수의 합보다 작을 수 있다.

## 저장 수와 저장 상태

사진 탭을 포함한 식당 상세의 공통 하단은 기존 API를 사용한다.

- `GET /api/v1/restaurants/save-counts?restaurantIds=123`: 해당 식당을 저장한 서로 다른 회원 수. 공개 조회 가능.
- `GET /api/v1/users/me/restaurant-saves?restaurantIds=123`: 로그인한 회원이 하나 이상의 컬렉션에 저장했는지. USER 토큰 필요.

저장·해제 성공 후 두 값을 다시 조회해서 모든 탭에 함께 반영한다. 마이페이지의 **내가 저장한 서로 다른 식당 수**는 이 API의 합계가 아니며, #259에서 별도로 다룬다.

## 구현 범위와 운영 확인

식당 대표·메뉴 참조는 `RestaurantPort`로 가져오며, 리뷰 테이블은 리뷰 모듈만 조회한다. 기존 `review → restaurant` 의존 방향을 유지하고 모듈 간 SQL 조인은 추가하지 않았다.

리뷰는 DB에서 집계·중복 제거하고 필요한 페이지까지만 앱으로 가져온다. 대표·메뉴 참조와 해당 asset projection은 전체를 읽는다. 기존 등록 API에 사진 수의 최대 제한이 없으므로 이 부분의 비용은 해당 식당의 대표·메뉴 사진 수에 비례한다. 새 입력 제한을 임의로 추가하지 않았다.

현재 리뷰 모델에는 별도의 숨김 상태나 숨김 API가 없다. 삭제된 리뷰 사진은 제외하며, 숨김 기능을 도입할 때는 이 조회 조건에도 반영해야 한다. 숨김 처리를 구현·검증한 것으로 간주하지 않는다.

이미지 파이프라인의 AWS 배포·활성화는 이 API 구현과 별도다. 비공개·삭제 asset의 원본 URL을 대신 노출하지 않으며, 이미지가 준비되지 않았으면 클라이언트는 상태를 확인해 기본 이미지를 표시한다.

대표·메뉴 asset은 잘린 HERO/MENU_DETAIL 대신 원본 비율을 유지하는 `PHOTO_DETAIL`을 사용한다. 이전 규격으로 처리된 asset에 이 파생본이 없으면 `UNAVAILABLE`, `imageUrl=null`을 반환한다. 이는 자동 처리 중이란 뜻이 아니므로 실제 이미지 파이프라인 준비 후 별도로 재처리해야 한다. 기존 파생본을 원본 비율이라고 안내하거나 private 원본으로 우회하지 않는다.
