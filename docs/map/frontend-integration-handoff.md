# 지도 프런트 연동 인계 — 2026-10-09

## 범위와 기준

서버 API 계약과 백엔드 검증을 정리한다. 화면 연결은 프런트에서 진행한다.

- 기획: HASHI-PLAN `4058a24`의 MAP_MAIN, MAP_FILTERED, MAP_RESTAURANT_DETAIL, RESTAURANT_SEARCH.
- 프런트 #210 스냅샷: `03636670dd5dafc4689f2ef8b8f607e2653c4c3b`. PR 본문에는 예전 정적 화면 설명이 있지만 최신 `MapPage.spec.md`/코드에는 Google SDK가 있다. 식당·지역 데이터와 저장/예약은 샘플·미연동이다.
- 서버: #236 기존 결합본 및 #251 관리자 지역 설정 작업. 서버 PR은 아직 병합·배포하지 않았다.
- Figma는 디자인 파일의 `UI [디자인 2차 스프린트] > 지도`와 기획 파일의 `MAP_MAIN`을 읽기 전용으로 대조했다. 카테고리, 관광 지역 클러스터, 식당 카드와 바텀시트 구성은 확인했지만 정적인 프레임으로 재시도·상태 복원 동작까지 검증한 것은 아니다. 동작 기준은 위 기획 문서이며, 화면 연결과 최종 UI QA는 프런트 담당자가 진행한다.

## 연결 순서

1. `GET /api/v1/restaurants/map/regions`에서 `initialBounds`, `queryLimits`, `regions`를 받는다. 지역의 `mapRegionId`, `clusterPosition`, `cameraBounds`, `restaurantCount`를 사용한다. 샘플 `areaCode`를 서버 ID로 변환한다고 가정하지 않는다.
2. 지역 선택 시 cameraBounds를 맞추고 `GET /api/v1/restaurants/map?south=...&north=...&west=...&east=...&mapRegionId=...`를 요청한다. cameraBounds는 대표 화면이며 식당의 소속 경계를 계산하는 다각형이 아니다. 소속은 관리자 API로 지정한다.
3. 새 조회는 네 bounds가 필수이며 `mapRegionId`, `keyword`, `genre`, `placeType`, `sort`를 선택적으로 보낸다. sort/분류의 wire 값은 서버 계약과 생성된 API 타입을 따른다.
4. 추가 조회는 `cursor`만 보낸다. bounds나 필터를 섞으면 400이다. `content`와 핀을 함께 추가하고 hasNext=false면 중단한다.
5. 같은 bounds·필터에서 정렬만 바꾸면 `querySessionId`와 `sort`만 보내 기존 추천 동점 순서를 유지한다. 카메라가 움직였거나 검색·카테고리·지역 조건이 달라졌다면 새 bounds/조건으로 새 조회를 만든다. 기존 sessionId에 새 필터를 섞지 않는다.
6. 식당 저장 관계는 기존 컬렉션 API를 사용한다. 지도 카드 자체에는 개인 저장 여부·저장 수가 없으므로 기존 bulk 저장 정보 API를 함께 연결한다. 선택한 컬렉션은 `GET /api/v1/collections/{id}/map-markers`의 모든 유효 핀을 표시한다.

## 최신 기획과 맞출 화면 동작

- 지도 pan/zoom만으로 식당 목록을 자동 재조회하지 않는다. 카메라 이동과 마지막 조회 bounds를 따로 보관한다.
- 지도 이동 시 바텀시트를 최소 높이로 줄인다. 카테고리가 있을 때 마지막 조회 bounds와 달라지면 현재 위치 검색 버튼을 표시한다. 카테고리가 없는 전체 상태에서는 버튼을 숨긴다.
- 사용자가 지역 선택 후 지도를 움직이면 지역 선택 맥락을 해제한다. 다음 신규 조회에 예전 mapRegionId를 남기지 않는다.
- 검색·카테고리가 없을 때 축소 줌 기준에서 지역 클러스터로 복귀한다. #210의 현재 ‘명시적 reset에서만 복귀’와 차이가 있으므로 담당자가 수정해야 한다. SDK 줌 기준 수치는 클라이언트 설정으로 관리한다.
- 현재 카테고리를 다시 누르면 카테고리를 해제한다. 검색/카테고리/정렬의 새 조회는 기존 목록·핀·스크롤을 초기화한다. 추가 페이지 실패 때만 기존 목록·핀을 유지한다.
- 요청 세대 또는 취소 신호로 이전 조건의 늦은 응답을 버린다. 최신 요청 중 카메라만 움직인 경우에는 기획에 따라 요청 당시 bounds로 돌아간 뒤 결과를 반영한다.
- 탭 이탈/백그라운드부터 5분간 화면 상태를 보존하며 그 이후 복귀나 활성 지도 탭 재선택은 초기화한다. 이는 Redis의 ‘마지막 성공 조회부터 유휴 5분, 전체 최대30분’과 다른 타이머다.

## 오류와 경계

- HTTP410 / RESTAURANT-013: 저장된 목록·핀은 그대로 두고 추가 조회 대신 새 조회를 안내한다. 새 결과와 만료 세션의 목록을 이어 붙이지 않는다.
- HTTP429 / RESTAURANT-022: 호출 제한. 즉시 무한 재시도하지 않는다.
- HTTP503: 비활성/키/Redis/예산 제한 등 서버 응답 코드를 구분하고 재시도 UI를 둔다. 설정 누락을 빈 목록 성공으로 표시하지 않는다.
- bounds는 지원 범위 안에서 위도·경도 폭 각각 최대1도다. 광역 화면은 지역 클러스터를 사용하고, 임의로 범위를 잘라 전체 결과라고 표시하지 않는다.
- 지도 검색은 요청한 현재 viewport 안에서 카테고리를 유지해 조회한다. 다른 지역까지 검색 범위를 넓히지 않는다.
- 지도에서 검색한 뒤에도 정렬은 `recommend`·`rating`·`reviews`를 사용한다. 2026-10-09 담당자 확인 사항이며, 일반 검색 화면의 정확도순·인기순 계약과 구분한다.
- ‘검색 결과 모두 fit’은 첫 페이지 10개가 아니라 해당 조건의 전체 결과에 적용한다. 검색 응답의 `searchResult.totalCount`와 `searchResult.bounds`를 사용한다. 0건은 bounds가 없고, 1건은 같은 남북·동서 경계이므로 해당 지점으로 이동한다. 검색어가 없는 일반 탐색에는 이 집계가 없다.
- 지도 조정은 검색 요청 당시 결과를 보여 주는 카메라 동작이다. 조정된 화면으로 즉시 다시 검색하면 조회 조건이 반복 변경되므로 자동 요청하지 않는다. 사용자가 새 검색이나 현재 위치 검색을 실행하면 그 시점의 viewport로 새 세션을 만든다.
- 지도 검색은 식당명·메뉴명·해시태그를 대상으로 공백으로 나눈 단어 중 하나라도 일치하면 찾는다. `#태그` 형식은 단일 해시태그 검색이며, 검색어는 앞뒤 공백 제거 후 30자 이하다. 기존 일반 검색 API의 정렬·커서 계약까지 이번 지도 변경으로 바뀌는 것은 아니다.

## 공개 전 준비

- 실제 지역 대표 위치·cameraBounds·식당 소속 데이터는 기획 승인 자료로 입력한다. 합성 fixture를 실제 초기 지역으로 배포하지 않는다.
- 브라우저 SDK 키/Map ID는 프런트의 `VITE_GOOGLE_MAPS_API_KEY`, `VITE_GOOGLE_MAPS_MAP_ID` 설정을 사용한다. 서버 Geocoding 키를 프런트에 복사하지 않는다.
- 테스트 환경에 서버 PR을 실제 반영하고 필요한 기능만 명시적으로 활성화한 뒤 프런트 담당자가 인증·비로그인·페이지 추가·세션 만료·저장 전체 핀을 검증한다.
- 백엔드 실호출 테스트와 로컬 부하 결과는 실제 브라우저/모바일 QA 및 운영 용량 보장이 아니다.


## 관리자 위치 확인 화면 제안

식당을 저장하면 Google 위치 확인은 별도 작업으로 처리한다. 저장 성공만으로 지도 핀이 생겼다고 표시하면 안 된다.
기존 식당 수정 화면에 작은 위치 확인 영역을 추가하는 것이 첫 단계다. 별도 대시보드는 확인 대상이 많아질 때 확장한다.

| 표시 항목 | 서버 계약과 처리 |
|---|---|
| 표시 주소 | `address`. 건물명·층수를 포함해 사용자에게 보여 줄 원문 |
| 위치 확인용 주소 | 선택 항목 `geocodingAddress`. 없으면 `address`로 조회. 일본어 주소를 모든 식당에 새로 입력하는 항목이 아님 |
| 처리 상태 | `UNRESOLVED`, `PENDING`, `READY`, `RETRY_WAIT`, `REVIEW_REQUIRED`, `FAILED`를 운영자가 이해할 말로 표시 |
| 확인 사유 | `failureCode`로 후보 없음, 후보 여러 개, 주소 불일치, 국가 정보 부족, 지원 지역 밖 등을 구분. provider 원문이나 키를 노출하지 않음 |
| 다음 시도·시도 횟수 | `nextAttemptAt`, `attempt`. 일시 장애는 서버가 자동 재시도하므로 중복 클릭을 유도하지 않음 |
| 다시 확인 버튼 | `canRetry=true`일 때 현재 `addressRevision`을 `expectedAddressRevision`으로 전달. 409면 최신 상태를 다시 읽음 |
| 유효기간 | `validUntil`. 갱신 중에도 아직 유효한 기존 좌표가 남을 수 있으므로 처리 상태만으로 핀 노출을 판단하지 않음 |

관리자 등록·수정 외에 다음 API를 제공한다.

| API | 사용 방법 |
|---|---|
| `GET /api/v1/admin/restaurants/locations` | 기본으로 `REVIEW_REQUIRED` 식당을 ID 오름차순으로 조회. `status`, 선택 `source`, 이전 응답의 `nextCursor`, `size`(기본 20, 최대 100)를 사용 |
| `GET /api/v1/admin/restaurants/{id}/location` | 수정 화면에서 해당 식당의 최신 상태와 주소 변경 번호를 확인 |
| `POST /api/v1/admin/restaurants/{id}/location/retry` | `canRetry`와 최신 `addressRevision`을 확인한 뒤 재처리 |

목록은 `restaurants`, `nextCursor`, `hasNext`를 반환한다. 상태가 바뀌는 작업 목록이므로 페이지 전체를 고정한 스냅샷은 아니다.
조회 도중 처리 상태가 바뀐 항목을 다시 확인하려면 첫 페이지부터 새로 읽는다. ADMIN 권한이 필요하고 응답은 캐시하지 않는다.
시설 내부 매장은 `READY`여도 실제 매장 위치와 다를 수 있으므로 `status=READY&source=GOOGLE_GEOCODING`으로도 점검할 수 있다.
지도에서 Places 후보를 고르고 확정하는 API는 아직 없다. 후속 계약은 `place-review-proposal.md`에 구분했다.

`REVIEW_REQUIRED`는 같은 주소를 자동으로 반복 호출하지 않는다. 관리자가 실제 지점과 주소를 확인해
위치 확인용 주소를 보완하거나 재처리를 요청한다. 식당이나 컬렉션 저장 관계를 삭제하지 않는다.
역·쇼핑몰 내부 매장은 주소 변환이 성공해도 시설 대표 위치일 수 있다. 이 경우 주소만 반복 조회하는 대신
식당명·지점명·주소로 Places 후보를 확인하는 후속 흐름이 필요하다. 현재 API가 후보 선택을 지원한다고 안내하면 안 된다.

## 실제 Google 추가 검증과 확장 범위

- 동일한 정상 주소를 대량 반복하기보다 확인 대상과 시설 내부 매장에 집중한다. 원문 입력을 보존하고 요청 방식, 응답 정확도, 선택한 지점의 일치 여부를 구분해 기록한다.
- Places API (New)는 별도 활성화·키 제한·호출 예산을 확인한 뒤 소량 검증한다. Text Search에 식당명·지점명·주소를 전달하고 필요한 필드만 요청한다. 첫 후보를 무조건 확정하지 않는다.
- 후보가 하나로 확인되면 place ID 중심의 확정·재확인 방식을 설계한다. 이는 provider 출처·수명·관리자 확인 이력을 포함하는 후속 API/DB 계약이며 현재 Geocoding 코드에 이미 구현된 기능이 아니다.
- 실제 프로젝트에서 처리 방식이 확인되면 격리된 개발 데이터로 등록 → 좌표 저장 → 갱신 → 확인 대상 재처리를 검증한다. 운영 backfill은 대상 수·예산을 먼저 확인하고 작은 범위부터 실행한다.
- Google 대량 부하는 하지 않는다. k6는 합성 식당과 mock provider를 사용한다.
- Routes API는 이번 구현에 포함하지 않는다. 향후 서비스 안에서 경로·이동 시간·복수 목적지 기능을 제공할 때 비용과 제품 요구를 다시 검토한다. 현재는 확장을 위한 빈 추상화나 dependency를 추가하지 않는다.

### Places 개발 프로젝트 실호출 확인 — 2026-10-09

개발 EC2에서 식당 3곳에 Text Search 3회, Place Details 3회, Geocoding 3회를 호출했다.
세 검색에서 각각 식당명·지점명이 일치하는 후보 하나를 받았고, 같은 place ID의 Details 위치와 검색 위치가 같았다.

| 식당 | Geocoding 주소 위치와 Places 매장 위치의 거리 |
|---|---:|
| 도쿄역 이카루가 | 약 208m |
| 키와미야 도쿄역점 | 약 11m |
| 마구로마트 | 약 4m |

Places를 쓰면 시설의 주소 위치와 특정 매장 위치를 구분할 수 있다는 확인이다.
지도 핀의 정확한 출입구·층 또는 식당 영업 상태까지 현장 검증한 결과는 아니다.
이 호출은 비교 실험이며 제품의 위치 저장·자동 갱신 흐름에 Places를 연결한 것은 아니다.
운영 DB와 Google 자동 처리 설정은 변경하지 않았고, 키·좌표 원문·응답 원문은 문서에 남기지 않는다.
