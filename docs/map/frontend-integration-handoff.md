## 연결 순서

1. `GET /api/v1/restaurants/map/regions`에서 `initialBounds`, `queryLimits`, `regions`를 받는다. 지역의 `mapRegionId`, `clusterPosition`, `cameraBounds`, `restaurantCount`를 사용한다. 샘플 `areaCode`를 서버 ID로 변환한다고 가정하지 않는다.
2. 지역 선택 시 cameraBounds를 맞추고 `GET /api/v1/restaurants/map?south=...&north=...&west=...&east=...&mapRegionId=...`를 요청한다. cameraBounds는 대표 화면이며 식당의 소속 경계를 계산하는 다각형이 아니다. 소속은 관리자 API로 지정한다.
3. 새 조회는 네 bounds가 필수이며 `mapRegionId`, `keyword`, `genre`, `placeType`, `sort`를 선택적으로 보낸다. sort/분류의 wire 값은 서버 계약과 생성된 API 타입을 따른다.
4. 추가 조회는 `cursor`만 보낸다. bounds나 필터를 섞으면 400이다. `content`와 핀을 함께 추가하고 hasNext=false면 중단한다.
5. 같은 bounds·필터에서 정렬만 바꾸면 `querySessionId`와 `sort`만 보내 기존 추천 동점 순서를 유지한다. 카메라가 움직였거나 검색·카테고리·지역 조건이 달라졌다면 새 bounds/조건으로 새 조회를 만든다. 기존 sessionId에 새 필터를 섞지 않는다.
6. 식당 저장 관계는 기존 컬렉션 API를 사용한다. 지도 카드 자체에는 개인 저장 여부·저장 수가 없으므로 기존 bulk 저장 정보 API를 함께 연결한다. 선택한 컬렉션은 `GET /api/v1/collections/{id}/map-markers`의 모든 유효 핀을 표시한다.

## 최신 기획과 맞출 화면 동작

- 지도 pan/zoom만으로 식당 목록을 자동 재조회하지 않는다. 카메라 이동과 마지막 조회 bounds를 따로 보관한다.
- 지도 이동 시 바텀시트를 최소 높이로 줄인다. 카테고리가 있을 때 마지막 조회 bounds와 달라지면 현재 위치 검색 버튼을 표시한다. 카테고리가 없는 전체 상태에서는 버튼을 숨긴다.
- 사용자가 지역 선택 후 지도를 움직이면 지역 선택 맥락을 해제한다. 다음 신규 조회에 예전 mapRegionId를 남기지 않는다.
- 검색·카테고리가 없을 때 축소 줌 기준에서 지역 클러스터로 복귀한다. #210의 현재 ‘명시적 reset에서만 복귀’와 차이가 있으므로 담당자가 수정해야 한다. SDK 줌 기준 수치는 클라이언트 설정으로 관리한다.
- 현재 카테고리를 다시 누르면 카테고리를 해제한다. 검색/카테고리/정렬의 새 조회는 기존 목록·핀·스크롤을 초기화한다. 추가 페이지 실패 때만 기존 목록·핀을 유지한다.
- 요청 세대 또는 취소 신호로 이전 조건의 늦은 응답을 버린다. 최신 요청 중 카메라만 움직인 경우에는 기획에 따라 요청 당시 bounds로 돌아간 뒤 결과를 반영한다.
- 탭 이탈/백그라운드부터 5분간 화면 상태를 보존하며 그 이후 복귀나 활성 지도 탭 재선택은 초기화한다. 이는 Redis의 ‘마지막 성공 조회부터 유휴 5분, 전체 최대30분’과 다른 타이머다.

## 오류와 경계

- HTTP410 / RESTAURANT-013: 저장된 목록·핀은 그대로 두고 추가 조회 대신 새 조회를 안내한다. 새 결과와 만료 세션의 목록을 이어 붙이지 않는다.
- HTTP429 / RESTAURANT-022: 호출 제한. 즉시 무한 재시도하지 않는다.
- HTTP503: 비활성/키/Redis/예산 제한 등 서버 응답 코드를 구분하고 재시도 UI를 둔다. 설정 누락을 빈 목록 성공으로 표시하지 않는다.
- bounds는 지원 범위 안에서 위도·경도 폭 각각 최대1도다. 광역 화면은 지역 클러스터를 사용하고, 임의로 범위를 잘라 전체 결과라고 표시하지 않는다.
- ‘검색 결과 모두 fit’의 전체 범위를 첫 페이지 10개로 계산하면 누락된다. 현재 페이지 응답에는 전체 결과의 bounds가 없으므로 검색 화면에서 전달하는 결과 범위와 조회 조건을 연결할 때 추가 확인해야 한다. 지도 검색과 검색 화면의 결과 범위를 같다고 임의 가정하지 않는다.

## 공개 전 준비

- 실제 지역 대표 위치·cameraBounds·식당 소속 데이터는 기획 승인 자료로 입력한다. 합성 fixture를 실제 초기 지역으로 배포하지 않는다.
- 브라우저 SDK 키/Map ID는 프런트의 `VITE_GOOGLE_MAPS_API_KEY`, `VITE_GOOGLE_MAPS_MAP_ID` 설정을 사용한다. 서버 Geocoding 키를 프런트에 복사하지 않는다.
- 테스트 환경에 서버 PR을 실제 반영하고 필요한 기능만 명시적으로 활성화한 뒤 프런트 담당자가 인증·비로그인·페이지 추가·세션 만료·저장 전체 핀을 검증한다.
- 백엔드 실호출 테스트와 로컬 부하 결과는 실제 브라우저/모바일 QA 및 운영 용량 보장이 아니다.
